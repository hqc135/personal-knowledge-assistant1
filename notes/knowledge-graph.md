
# 知识图谱：构建、存储、推理、与 LLM 结合

> 这个方向面试问得不算特别多，但一旦问到就会比较深。主要参考了 Stanford CS520 和一些综述论文。

## 核心概念

知识图谱本质上是一个**有向标记图**，基本单元是三元组：

```
(头实体, 关系, 尾实体)
(subject, predicate, object)

例：(北京, 是首都of, 中国)
    (张三, 就职于, 阿里巴巴)
    (阿里巴巴, 总部位于, 杭州)
```

### 和关系数据库的对比

| 特性 | 关系数据库 | 知识图谱 |
|------|-----------|----------|
| 数据模型 | 表格 | 图 |
| Schema | 强 schema | 灵活/无 schema |
| 查询 | SQL | SPARQL/Cypher |
| 擅长 | 结构化事务 | 关系推理、语义查询 |
| 多跳查询 | JOIN 很慢 | 图遍历天然支持 |

## 知识图谱构建 Pipeline

```
原始文本 → NER(命名实体识别) → 关系抽取 → 实体对齐 → 知识融合 → 存入图数据库
```

### 关系抽取的几种方法

1. **基于规则/模板**：准确但覆盖率低
2. **监督学习**：标注成本高，但效果好
3. **远程监督**：用已有 KG 自动标注训练数据（有噪声）
4. **LLM 抽取**：直接用 GPT-4 做 few-shot 抽取（当前最实用的方案）

```python
# LLM 做三元组抽取的 prompt 示例
prompt = """
从以下文本中抽取(实体, 关系, 实体)三元组：

文本："{text}"

输出格式：
[("实体1", "关系", "实体2"), ...]
"""
```

**面试高频考点**：远程监督的假设是什么？→ 如果知识库中存在关系 r(e1, e2)，那么包含 e1 和 e2 的句子都可能表达了关系 r。这个假设显然有噪声。

## 存储方案

### 图数据库

- **Neo4j**：最流行，Cypher 查询语言，适合中小规模
- **JanusGraph**：分布式，适合大规模
- **Amazon Neptune**：云原生，支持 SPARQL 和 Gremlin

### 向量化存储（Knowledge Graph Embedding）

把实体和关系映射到低维向量空间，用于链接预测和推理：

**TransE**（最经典）：

```
核心思想：h + r ≈ t （头实体向量 + 关系向量 ≈ 尾实体向量）

损失函数：
L = Σ max(0, γ + d(h+r, t) - d(h'+r, t'))

其中 (h,r,t) 是正样本，(h',r,t') 是负样本（随机替换头或尾）
γ 是 margin
```

**这里我一开始理解错了**：TransE 对 1-to-N 关系处理不好（比如"出生于"这种多对一关系），因为多个头实体 + 同一个关系向量会映射到同一个点。后续的 TransR、RotatE 就是为了解决这个问题。

**和 Word2Vec 的类比**：TransE 的 h + r ≈ t 和 Word2Vec 里 king - man + woman ≈ queen 的思想非常相似——都是在向量空间里用算术运算表达语义关系。

### 其他 KGE 方法

| 方法 | 核心操作 | 特点 |
|------|----------|------|
| TransE | 平移 h+r≈t | 简单高效，1-N 关系差 |
| TransR | 投影+平移 | 关系有独立空间 |
| RotatE | 旋转 h∘r≈t | 能建模对称/反对称/组合关系 |
| ComplEx | 复数空间内积 | 能建模反对称关系 |

## 知识图谱推理

### 基于规则的推理

```
规则：father(X,Y) ∧ father(Y,Z) → grandfather(X,Z)
```

传统方法用 Datalog 或 Prolog 做逻辑推理。

### 基于 embedding 的推理（链接预测）

给定 (h, r, ?)，找最可能的尾实体：

```python
# TransE 链接预测
scores = {}
for candidate_t in all_entities:
    scores[candidate_t] = -distance(h + r, candidate_t)
predicted_t = argmax(scores)
```

评估指标：MRR（Mean Reciprocal Rank）、Hits@K

### 基于 GNN 的推理

用图神经网络在 KG 上做消息传递，学习实体的上下文表示。**这和 Transformer 的 attention 有相似之处**——都是聚合邻居信息，只不过 GNN 是在图结构上，Transformer 是在序列上（全连接图）。

## 知识图谱 + LLM：当前热点

### 三种结合方式

1. **KG 增强 LLM**（检索增强）
   - 查询相关子图 → 序列化为文本 → 注入 prompt
   - 类似 RAG，但检索的是结构化知识而非文档片段

2. **LLM 增强 KG**（知识抽取/补全）
   - 用 LLM 做实体识别、关系抽取、知识补全
   - 比传统 NLP pipeline 效果好很多

3. **LLM 与 KG 协同**（GraphRAG）
   - 微软的 GraphRAG：先用 LLM 构建文档的知识图谱，再基于图结构做社区检测和摘要
   - 对全局性问题（"这个数据集的主要主题是什么"）效果远好于普通 RAG

```python
# GraphRAG 的简化流程
documents → LLM抽取实体和关系 → 构建图 → 社区检测(Leiden算法) 
→ 每个社区生成摘要 → 查询时检索相关社区摘要 → LLM生成答案
```

### 实际应用中的坑

- KG 的覆盖率永远不够，需要和向量检索互补
- 实体消歧很难（"苹果"是公司还是水果？）
- 图的序列化方式对 LLM 理解影响很大（三元组列表 vs 自然语言描述 vs 结构化格式）

## 和其他主题的交叉

1. **和 Agent 框架的关系**：KG 可以作为 Agent 的工具——Agent 通过 SPARQL/Cypher 查询 KG 获取精确的结构化知识，比纯文本检索更可靠
2. **和联邦学习的关系**：跨机构的知识图谱构建涉及数据隐私问题，联邦知识图谱嵌入（FedE）是一个研究方向
3. **和多模态的关系**：多模态知识图谱（MMKG）把图像、文本、结构化知识统一表示，实体不仅有文本描述还有视觉特征
